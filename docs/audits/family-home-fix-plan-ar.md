# خطة إصلاح Family Home — مهام صغيرة قابلة للتتبع

**آخر تحديث:** 22 أكتوبر 2026  
**الفرع:** `audit/full-site-security-performance-2026-10-22`  
**قاعدة العمل:** إعدادات `.htaccess` وحدود PHP المكتوبة في المستودع تُعامل كإعدادات إنتاج مستخدمة، حسب تأكيد مالك الموقع. لا يعني ذلك أن كل توجيه Apache فعال بالضرورة في كل نوع استضافة؛ تُراجع ترويسات الاستجابة وإعدادات PHP الفعلية قبل تغييرها.

## قواعد التنفيذ

- كل مهمة تطبيقية في فرع إصلاح منفصل مشتق من آخر `main` مستقر، مع PR مستقل عندما تكون مخاطرة التغيير أو نطاقه كبيرًا.
- لا تغيّر إعدادات الإنتاج أو قاعدة البيانات مباشرة أثناء التشخيص.
- كل مهمة تذكر اختبار قبول واضحًا؛ أما المهام التي تعدّل الموقع فتشغّل `php artisan test` و`npm run lint` و**`npm run build`** واختبارات Playwright ذات الصلة على الفرع نفسه.
- `npm run build` إلزامي لكل تغيير يؤثر في الموقع؛ يجب أن يكمل client + SSR + prerender.
- لا دمج ولا نشر مع فشل اختبار أو نتيجة غير معروفة. لا تستخدم Playwright ضد الإنتاج لاختبار إصلاح مقترح.
- دوّن قبل وبعد كل تغيير: القياس، نتيجة CI، الملفات المتغيرة، وطريقة التراجع.

## المرحلة 1 — منع أخطاء الإنتاج والمخاطر عالية الأولوية

### FH-01 — إصلاح حدود رفع الصور لتناسب حد الطلب
**الأولوية:** P0 · **الحجم:** M · **الاعتماد:** FH-00

المشكلة: كل صورة قد تصل إلى 5 MiB، بينما الطلب الواحد يخضع لحد `post_max_size=64M`؛ قد يتجاوز طلب واحد الحد عند رفع عدة صور حتى لو كانت كل صورة صالحة.

- [ ] مراجعة `UnitFormRequest` و`ProjectFormRequest` ومكوّنات رفع الصور وطريقة إرسال النموذج.
- [ ] الحل الآمن الأول: حد أقصى 8 صور جديدة في الطلب الواحد، مع حد 5 MiB للصورة، ورسالة عربية/إنجليزية واضحة عند تجاوز الحد. تبقى الصور القديمة محفوظة.
- [ ] إذا كان رفع 20 صورة دفعة واحدة شرطًا للعمل، افتح مهمة لاحقة لرفعها على دفعات متتابعة لا تتجاوز 8 صور في الطلب بدل رفع 20 ملفًا في طلب واحد.
- [ ] أضف اختبارًا يثبت رفض الطلب الزائد بطريقة مفهومة، واختبارًا لرفع الحد المقبول.

**معيار القبول:** لا يصل طلب صورة طبيعي إلى حد PHP دون رسالة واضحة، ولا تُفقد الصور التي سبق حفظها، ويعمل الرفع على الاستضافة التجريبية نفسها.

### FH-02 — فصل كاش ملفات Vite ذات البصمة عن الصور ذات الاسم الثابت
**الأولوية:** P0 · **الحجم:** S

المشكلة: `.htaccess` يضع كاشًا لمدة سنة على أسماء صور ثابتة مثل `/images/hero.webp`، وكذلك على ملفات build الممهورة ببصمة. تخزين ملفات Vite الممهورة سنة مناسب؛ أما الملفات الثابتة بالاسم نفسه فقد تبقى قديمة بعد استبدالها.

- [ ] تعديل سياسة الكاش بحيث يظل الكاش الطويل محصورًا بالأصول الممهورة ببصمة، مثل `/build/assets/*-HASH.js` و`*.css`.
- [ ] اجعل الصور ذات الاسم الثابت قصيرة الكاش أو تتطلب إعادة تحقق، أو غيّر أسماءها مع كل تحديث.
- [ ] اختبر ترويسات الاستجابة بعد تغيير `.htaccess` على staging؛ تحقق كذلك من عدم تعارض Cloudflare مع ترويسات الأصل.

**معيار القبول:** ملفات build ذات البصمة تحصل على كاش طويل، بينما `hero.webp` وملفات الصور الثابتة لا تبقى قديمة سنة بعد التحديث.

### FH-03 — توحيد المضيف الأساسي والتحويل إلى HTTPS
**الأولوية:** P0 · **الحجم:** S

المشكلة: قاعدة HTTPS الحالية تستخدم `%{HTTP_HOST}` في عنوان التحويل، ولا يظهر في الملف توحيد صريح بين `www` وبدونه. اختلاف المضيف يؤثر في canonical والتكرار، وقد يعكس Host غير موثوق في إعدادات خادم غير ملائمة.

- [ ] اعتماد `https://familyhome-co.com` كمضيف أساسي، بعد التأكد من الإعداد المعتمد في لوحة النطاق.
- [ ] إجراء تحويل دائم واحد من HTTP وأي مضيف بديل إلى HTTPS والمضيف المعتمد باستخدام وجهة ثابتة، مع مراعاة Cloudflare/proxy.
- [ ] اختبار طلبات Host البديلة وطلب HTTP، والتأكد من عدم حدوث redirect loop.
- [ ] مطابقة `APP_URL` والـ sitemap وcanonical وhreflang مع المضيف الأساسي.

**معيار القبول:** كل النسخ البديلة تنتهي بتحويل واحد فقط إلى HTTPS والمضيف المعتمد، ولا ينتج تحويل إلى مضيف يقدمه طالب الطلب.

### FH-04 — ضمان استثناء الصفحات الحساسة من كاش CDN
**الأولوية:** P0 · **الحجم:** S

- [ ] مراجعة Cache Rules الفعلية في Cloudflare، إن كانت مستخدمة، إلى جانب `HttpCacheControl` داخل Laravel.
- [ ] استثناء `/admin` وlogin/reset/profile وصفحات النماذج مثل contact وتفاصيل الوحدة/المشروع التي تحمل CSRF token، وكل طلب Inertia، من الكاش العام.
- [ ] إبقاء الكاش العام فقط لصفحات GET العامة التي لا تحمل بيانات خاصة بالجلسة.
- [ ] اختبر HTML وInertia JSON من خلال الترويسات؛ جرّب مستخدمين وجلسات ولغتين مختلفتين.

**معيار القبول:** لا تُعاد صفحة أو CSRF token أو بيانات جلسة من مستخدم إلى مستخدم آخر، وتظهر ترويسات الكاش المتوقعة لكل نوع مسار.

### FH-05 — التأكد من خدمة الصور الثابتة مباشرة
**الأولوية:** P1 · **الحجم:** S

- [ ] تحقق من وجود رابط `public/storage` الصحيح ومن أن `DocumentRoot` يوجّه إلى مجلد `public` في بيئة الإنتاج.
- [ ] افحص مسار `/storage/{path}` الاحتياطي في Laravel؛ حدد ما إذا كانت طلبات الصور الصحيحة تصل إليه بدل خادم الملفات الثابتة.
- [ ] أصلح DocumentRoot/الرابط إذا ثبت أن الصور الصحيحة تمر عبر PHP، ولا تحذف fallback قبل اختبار الصور القديمة والمفقودة.

**معيار القبول:** الصورة الموجودة تُخدم كملف ثابت مباشرة، مع النوع والحجم الصحيحين، والصورة المفقودة ما زالت تعرض fallback مناسبًا.

## المرحلة 2 — إصلاحات السرعة، بالترتيب حسب القياس

- [ ] احسب CSS المستخدم فعليًا في الصفحات العامة عبر Coverage.

- [ ] احذف فقط الأنماط التي أثبت القياس عدم استخدامها؛ تحقّق من RTL/LTR والجوال والداكن والفاتح.
- [ ] سجل فرق حجم CSS الخام والمضغوط، وعدد التحذيرات، وLCP بعد التغيير.

**معيار القبول:** تحسن قابل للقياس في CSS المنقول دون فقد أي نمط في صفحات العامة أو الإدارة.

### FH-07 — الحفاظ على تقسيم حزم الإدارة وعدم تحميلها للزوار
**الأولوية:** P1 · **الحجم:** S

- [ ] راجع manifest وNetwork على الصفحة الرئيسية وصفحة قائمة الوحدات.
- [ ] تأكد أن Tiptap وRecharts وأي حزمة خاصة بالإدارة لا تُحمّل في صفحات الزوار ما لم تكن مطلوبة فعلًا.
- [ ] لا تغيّر إعدادات chunks لمجرد حجم الحزمة؛ التعديل يتم فقط إذا أظهر Network أنها تؤثر على الحزمة الأولية.
- [ ] قارن JS المنقول في التحميل الأول قبل/بعد.

**معيار القبول:** الحزم الإدارية تُحمّل من صفحات الإدارة فقط، ولا يزيد حجم التحميل الأول للصفحات العامة.

### FH-08 — إنهاء سياسة الصور المتجاوبة والتحميل الكسول
**الأولوية:** P1 · **الحجم:** M

- [ ] تحقق من أن صورة LCP فقط لها `fetchpriority=high` وأن `preload` يطابق الصورة الفعلية و`srcset/sizes`.
- [ ] تحقق أن صور المحتوى أسفل الجزء المرئي تستخدم `loading=lazy` وأبعادًا ثابتة لمنع CLS.
- [ ] تأكد أن صفحات العقارات تستخدم صور `thumb/medium/large` المناسبة لا الصورة الأصلية الكبيرة في بطاقات العرض.
- [ ] اختبر الشبكة على هاتف محاكى وعلى صور فعلية من التخزين، بما في ذلك الصور القديمة والمفقودة.

**معيار القبول:** لا يوجد preload مكرر أو للصورة الخطأ، والبطاقات لا تنقل صورًا أصلية كبيرة دون حاجة، ولا يرتفع CLS.

### FH-09 — تثبيت توليد WebP ومراقبة طابور الصور

- [ ] في staging، ارفع صورة صحيحة كبيرة وصورة غير قابلة للفك واختبر نتيجة المهمة والمحاولات والسجل.

- [ ] أضف تنبيهًا أو تقريرًا دوريًا للمهام الفاشلة قبل أي تعديل إضافي في الخوارزمية.

**معيار القبول:** النسخ المصغرة تولّد، الفشل يظهر بوضوح مع retry، والأصل يبقى متاحًا عند فشل النسخة المحسّنة.

### FH-10 — تحسين استعلامات قواعد البيانات بالقياس لا بالتخمين
**الأولوية:** P1 · **الحجم:** M/L

- [ ] اجمع الاستعلامات الأبطأ من صفحات القائمة والتفاصيل وHome على staging ببيانات قريبة من الإنتاج.
- [ ] شغّل `EXPLAIN` للاستعلامات البطيئة وتحقق من الفهارس الحالية قبل إضافة فهارس جديدة.

- [ ] تحقق من eager loading/withCount في صفحات العرض، وتجنب تحويل كل النتائج إلى eager loading إضافي دون دليل.
- [ ] قارن زمن الاستعلامات، وعددها لكل طلب، وزمن الاستجابة قبل/بعد.

**معيار القبول:** كل تعديل مرتبط باستعلام بطيء موثق ويقل زمنه أو كلفته في الاختبار، ولا يتدهور مسار كتابة البيانات.

### FH-11 — قياس إعدادات CDN والضغط على الاستجابة الفعلية
**الأولوية:** P1 · **الحجم:** S

- [ ] اختبر هل HTML وCSS وJS وWebP تُقدّم بضغط Brotli/Gzip المناسب فعلًا؛ وجود إعداد في دليل لا يثبت تفعيله.
- [ ] تحقق من HTTP/2 أو HTTP/3 وCache HIT/MISS وTTFB من خارج الخادم.
- [ ] لا تفعّل/تعدل قواعد Cloudflare العامة قبل تأكيد استثناء كل صفحة خاصة/ذات CSRF.
- [ ] سجّل حجم الاستجابة بعد الضغط لا الحجم الخام فقط.

**معيار القبول:** دليل من ترويسات الاستجابة بأن الضغط والكاش يعملان كما هو مقصود، مع استمرار استثناء المسارات الحساسة.

## المرحلة 3 — صحة البيانات وSEO وتقوية الأمان

### FH-12 — تدقيق canonical وhreflang وSitemap
**الأولوية:** P1 · **الحجم:** M

- [ ] اجمع عينة من روابط الوحدات والمشروعات والمقالات بالعربية والإنجليزية.
- [ ] تحقق من أن كل loc في sitemap يرجع 200 أو تحويلًا مقصودًا، وأن كل لغة تستخدم slug الصحيح.
- [ ] تحقق من عدم إدراج صفحة غير منشورة/غير نشطة، ومن عدم وجود عنوان مضيف مزدوج أو localhost.
- [ ] اختبر XML آليًا ومن سجلات Search Console إن كانت متاحة.

**معيار القبول:** لا توجد روابط broken أو slugs لغة خاطئة في العينة، canonical/hreflang متسقان مع المضيف الأساسي، وملفات sitemap صالحة.

### FH-13 — تنظيف أخطاء الترميز في بيانات المحتوى
**الأولوية:** P2 · **الحجم:** M

- [ ] ابحث عن التكرار غير الطبيعي مثل `&amp;amp;` و`&amp;amp;amp;` في حقول slug/title/description والروابط.
- [ ] أنشئ تقريرًا للصفوف المتأثرة دون تعديلها تلقائيًا.
- [ ] اختبر تحويلًا آمنًا على staging؛ لا تعمل double-decode على HTML صحيح.
- [ ] أصلح السجلات المؤكدة بنسخة احتياطية وسجلًا يوضح القيم قبل/بعد.

**معيار القبول:** تختفي حالات الترميز المكررة المؤكدة من الصفحات المختبرة ولا تنكسر علامات ampersand أو النصوص العربية الصحيحة.

### FH-14 — تقليل الاستثناءات الصامتة وتحسين الرصد
**الأولوية:** P2 · **الحجم:** M

- [ ] راجع `catch` الفارغة في model cache invalidation وHomeController وSettingsService.
- [ ] استبدل إخفاء الخطأ بتسجيل منظم محدود لا يكشف أسرارًا أو بيانات شخصية، مع fallback مقصود عندما تكون الصفحة قابلة للعمل جزئيًا.
- [ ] أضف اختبارًا لحالة تعطل cache/database يضمن ألا تعرض الصفحة فشلًا صامتًا مضللًا.
- [ ] لا تسجّل IP أو email أو payload حسّاسًا دون حاجة موثقة.

**معيار القبول:** الفشل قابل للتشخيص من logs، مع بقاء الـ fallback متوقعًا، وبدون تسريب بيانات حساسة.

### FH-15 — تقوية CSP تدريجيًا
**الأولوية:** P2 · **الحجم:** M/L

- [ ] اجمع تقارير CSP بعد الإصلاحات الأساسية وصنّف المصادر الحقيقية اللازمة.
- [ ] حصر `unsafe-inline` ثم خطة nonce/hash على staging؛ لا تحذفها دفعة واحدة قبل التأكد من analytics والخرائط وYouTube وInertia.
- [ ] اختبر نماذج التواصل والتحليلات والخرائط والفيديو والمتصفح بلا JavaScript.

**معيار القبول:** تقل صلاحيات CSP غير الضرورية دون منع الوظائف المطلوبة أو كسر التنقل.
