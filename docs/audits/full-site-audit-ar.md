# تقرير التدقيق الفني الشامل لموقع Family Home

**تاريخ المراجعة:** 22 أكتوبر 2026  
**المستودع:** `mohamedalgepry/family-home-laravel-wab`  
**نطاق المراجعة:** كود Laravel، المسارات والـ middleware، التحقق والصلاحيات، خدمات واستعلامات العقارات، رفع الصور وتوليد النسخ، React/Inertia، CSS، SEO/Sitemap، البناء وSSR/Prerender، GitHub Actions وPlaywright، والملفات الثابتة الموجودة في `public/build`.

## حدود المراجعة

هذا تقرير مراجعة للكود وإعدادات المشروع. لا توجد لدي صلاحية مباشرة إلى قاعدة بيانات الإنتاج أو سجلات الخادم، ولم أشغّل Lighthouse/PageSpeed على متصفح متصل بالموقع؛ لذلك لا أقدّم رقمًا لدرجة السرعة أو Core Web Vitals ولا أصف أي قياس لم يحدث. أحجام الملفات أدناه هي أحجام الملفات المبنية المتتبعة في Git كما كانت على `main` وقت الفحص، قبل ضغط HTTP؛ وليست أحجام النقل الفعلية بعد Brotli/Gzip.

## إصلاحات أُجريت على فرع المراجعة

### 1. موثوقية البناء وPrerender — خطورة عالية

- كان أمر تصدير صفحات prerender يستطيع كتابة مصفوفة فارغة عند تعذر الاتصال بقاعدة البيانات ثم يرجع نجاحًا.
- كان سكربت `npm run build` يتجاوز مرحلة prerender عندما يقل العدد عن 10 صفحات، مع تحذير فقط. بالتالي يمكن أن ينجح البناء ظاهريًا من دون إنشاء صفحات HTML المطلوبة.
- كان تصدير البيانات قادرًا على استخدام بيانات مخزّنة قديمة بعد فشل التصدير الحالي، كما لم يكن يضمن أن كل المسارات المطلوبة أنتجت قالبًا صالحًا.
- كان اختبار المنفذ الخاص بـ SSR يحاول استدعاء `POST /shutdown`، بينما خادم `resources/js/ssr.jsx` لا ينفّذ هذا المسار؛ لذا كان من الممكن الاتصال بعملية قديمة واستعمال حزمة SSR غير الحالية. لم يكن لطلب SSR حدّ زمني واضح.

**الإجراء:** أصبح تعذر قاعدة البيانات أو عدم اكتمال تصدير الصفحات خطأً فعليًا، وأصبحت استجابات HTTP من نوع 4xx/5xx أثناء التصدير تُرفض. كما يرفض سكربت prerender العمل عند انشغال منفذ SSR، ويحدد 30 ثانية لطلب render. وأُضيف إعداد قاعدة بيانات مهيأة ومهاجرة ومملوءة ببيانات seed إلى مسار CI قبل تنفيذ `npm run build`.

**معيار القبول:** يجب أن ينجح `npm run build` كاملًا (client + SSR + prerender) ويولّد ملفات سليمة؛ نجاح Vite وحده لا يكفي.

### 2. اختبارات المتصفح والتحقق من فرع الإصلاح — خطورة عالية

- كانت اختبارات Playwright في GitHub Actions موجّهة إلى `https://familyhome-co.com` حتى عند فحص Pull Request؛ أي أنها كانت تختبر نسخة الإنتاج بدل الكود المقترح.
- كانت صلاحية `contents: write` ممنوحة على مستوى workflow كله، رغم أن معظم خطوات CI لا تحتاج كتابة المستودع.

**الإجراء:** أصبح Playwright يشغّل التطبيق المحلي من الـ checkout الحالي مع قاعدة بيانات الاختبار، ما يجعل الاختبارات تقيس فرع التغيير. أصبحت الصلاحية الافتراضية `contents: read`، ونُقلت كتابة ملفات البناء إلى job منفصلة لا تعمل إلا بعد نجاح الاختبارات على push إلى `main`. هذه المهمة المنفصلة مخصصة فقط لمزامنة ملفات `public/build` المولّدة مع نموذج النشر الحالي، ويجب التحقق من نجاحها في سجل Actions أيضًا.

### 3. التخزين المؤقت للتحويلات — خطورة متوسطة

كان المسار `/` يعيد تحويلًا دائمًا 301 اعتمادًا على لغة محفوظة في الجلسة، في حين أن middleware يستطيع وضع ترويسة تخزين عام للردود. قد يثبت المتصفح أو وسيط التخزين تحويل اللغة لمستخدمين آخرين أو بعد تغيير اللغة.

**الإجراء:** أصبح التحويل 302 مؤقتًا، وأصبح middleware يضع سياسة عدم التخزين على ردود 3xx و4xx/5xx. أُضيف اختبار يغطي تحويل الصفحة الرئيسية وترويسة `no-store`.

### 4. أولوية صورة الصفحة الرئيسية — تحسين LCP

أُعيد ترتيب منطق preload في قالب HTML بحيث يتم تفضيل مرشّحي صورة الـ Hero المتجاوبين على صورة Open Graph العامة عندما تكون الصفحة الرئيسية هي المطلوبة. أُضيف اختبار يتأكد من تضمين `hero-mobile.webp` و`hero.webp` كصور preload. يجب بعد البناء التأكد من عدم وجود تحميل مسبق مكرر باستخدام تقرير الشبكة/Lighthouse على نسخة فعلية.

### 5. مؤشرات التركيز بلوحة المفاتيح — خطورة متوسطة

كان إظهار `:focus-visible` محصورًا في أجهزة المؤشر الدقيق داخل media query؛ وقد تختفي علامة التركيز في بعض أجهزة اللمس والهجين عند استخدام لوحة مفاتيح.

**الإجراء:** أصبحت قاعدة `:focus-visible` عامة على جميع الأجهزة.

### 6. نقطة استقبال CSP — خطورة متوسطة

كان المسار `POST /csp-report` مستثنى من CSRF، دون تحديد حجم واضح للطلب أو تقييد للمعدل، وكان يسجّل كامل الحمولة وعنوان IP وUser-Agent. هذا يفتح احتمال إغراق السجلات وجمع بيانات لا تلزم لتشخيص السياسة.

**الإجراء:** حد أقصى 16 KiB للطلب، وتحديد 60 طلبًا في الدقيقة، وقصر البيانات المسجلة على حقول تشخيصية محددة. أُضيفت اختبارات لقبول تقرير محدود ورفض تقرير كبير.

## نتائج الأداء التي تحتاج قياسًا/متابعة

### A. CSS العام أكبر عنصر ثابت ظاهر في الملفات المبنية

في `main` وقت المراجعة، حجم `public/build/assets/app-BsJBqgjG.css` هو قرابة **149 KiB خامًا**. ملف CSS العام يؤثر في جميع الصفحات التي تستورده، لذلك يستحق تحليل التغطية الفعلية للـ CSS ومراجعة الأنماط المكررة. لا يمكن استنتاج حجم النقل النهائي أو أثره على LCP دون قياس الضغط والتخزين المؤقت وسلوك الشبكة.

### B. حزم كبيرة موجودة، لكنها تبدو مخصصة للوحة الإدارة

- `vendor-tiptap`: قرابة **394 KiB خامًا**.
- `vendor-recharts`: قرابة **330 KiB خامًا**.
- `vendor-react`: قرابة **210 KiB خامًا**.

تُظهر بيانات manifest أن Tiptap مرتبط بصفحات إدارية مثل نماذج المقالات/about، وأن Recharts مرتبط بلوحة الإدارة. لذلك لا ينبغي جمع هذه الأحجام على أنها تكلفة الصفحة الرئيسية مباشرة؛ المطلوب التحقق عبر Network Coverage أن هذه الحزم لا تُحمّل من صفحات الزوار العامة دون حاجة.

### C. سياسة Cache-Control للصور بأسماء غير ممهورة ببصمة

تضبط `.htaccess` مدة تخزين طويلة (سنة) على الصور وملفات CSS/JS والخطوط. هذا مناسب للأصول الممهورة ببصمة Vite مثل `/build/assets/*-HASH.js`، لكن أسماء ثابتة مثل `/images/hero.webp` قد تبقى نسخة قديمة في المتصفح بعد استبدال الملف بالاسم نفسه. يوصى بقصر مدة الكاش الطويلة على الأصول ذات الأسماء الممهورة ببصمة، أو تغيير اسم الصورة عند النشر؛ يجب اختبار ترويسات الاستضافة قبل تعديلها.

### D. إعدادات Cache والـ Queue

يعرض `.env.example` إعداد `CACHE_STORE=database` و`QUEUE_CONNECTION=database`. إذا كان الإنتاج يستخدم هذه القيم فعلًا، فإن زيارات صفحات التفاصيل قد تتسبب في عمليات cache متزامنة مع قاعدة البيانات وإدخال مهام التسجيل في queue. لا يمكن افتراض أن الإنتاج يستخدم القيم نفسها. افحص قيم بيئة الإنتاج وسجلات زمن الاستجابة أولًا؛ عند توافر Redis، يُفضّل تقييمه للكاش والـ queue، مع جعل منع تكرار عدّ الزيارات عملية ذرية بدل نمط `has` ثم `put`.

### E. اختيار مقالات عشوائية

في صفحة المقال، إذا لم يتوفر عدد كافٍ من المقالات في التصنيف، يستخدم الاستعلام `inRandomOrder()` لاختيار مقالات إضافية. ترتيب عشوائي على جدول كبير قد يكلّف أكثر من ترتيب محدود مفهرس. لا يُوصى بتغيير المنطق قبل قياس الاستعلام وبياناته؛ يمكن استخدام ترتيب حتمي أو تخزين المقالات المقترحة مؤقتًا إن أثبت القياس الحاجة.

### F. مسار الصور الاحتياطي

يوجد مسار Laravel مخصص لخدمة `/storage/{path}` عند عدم توفر الملف مباشرة، ويرجع صورة بديلة عند فقد بعض الصور. عادةً يجب أن يخدم خادم الويب الملفات الثابتة مباشرة عبر رابط التخزين الصحيح، لا عن طريق PHP. إذا أظهرت سجلات الخادم أن طلبات الصور تمر عبر هذا المسار بكثرة، افحص رابط `public/storage` وإعدادات DocumentRoot بدل الاعتماد على PHP لخدمة كل صورة.

## مخاطر أخرى تحتاج متابعة

1. **CSP:** السياسة تتضمن `'unsafe-inline'` في `script-src` و`style-src`. هذا ليس دليلًا بحد ذاته على وجود XSS، لكنه يقلل فاعلية CSP كدفاع إضافي. الانتقال إلى nonce/hash يحتاج فحص جميع السكربتات والتحليلات ومشغلات الفيديو/الخرائط على نسخة staging.
2. **روابط الصور الخارجية:** دالة `getStorageUrl` تقبل عناوين `http://` كما هي. أي عنوان خارجي غير آمن داخل صفحة HTTPS قد يُحجب كـ mixed content؛ يجب حصر البيانات الموجودة فعليًا ثم تطبيع الروابط إلى HTTPS عند دعم المضيف ذلك.
3. **معالجة أخطاء إبطال الكاش:** توجد مواضع في models تستخدم `catch` فارغة عند فشل تنظيف الكاش، كما توجد عمليات `catch` واسعة في بعض migration الخاصة بالفهارس. هذا قد يخفي بيانات قديمة أو index غير منشأ. لا ينبغي تعديل migrations تاريخية أو تنفيذ تغييرات قاعدة بيانات على الإنتاج قبل مراجعة حالة الفهارس الفعلية.
4. **تعديل URL/History على مستوى المتصفح:** يوجد تغليف مخصص لـ `URL` و`history.pushState/replaceState` في `resources/js/app.jsx` مع تجاهل بعض الاستثناءات. يحتاج اختبارًا منفصلًا قبل إزالته، لأنه قد يخفي أخطاء توجيه أو يحوّل الروابط غير الصالحة إلى localhost.
5. **حدود الرفع:** قواعد وحدات العقارات تسمح حتى 20 صورة، بحد 5 MiB للصورة. هذا سقف يصل إلى 100 MiB قبل احتساب الطلب، بينما `.htaccess` يذكر `post_max_size=64M` في بيئات mod_php. يجب التأكد من إعدادات PHP الفعلية في الاستضافة؛ فالرفع المتعدد قد يفشل إذا تجاوز إجمالي الطلب حد الخادم حتى عندما تجتاز كل صورة التحقق منفردة.

## نقاط جيدة تم التحقق منها في الكود

- توجد سياسات Laravel مسجلة للوحدات والمشروعات والمقالات والإعدادات وغيرها، وتستخدم بعض FormRequests التحقق من صلاحية المستخدم على السجل.
- يوجد sanitizer للمحتوى الغني واختبارات لهجمات روابط JavaScript وملفات SVG/HTML.
- توجد قيود رفع للصور تشمل الأنواع والأحجام والأبعاد، وتُنفّذ توليدات الصور المصغرة كـ Queue Job بدل تنفيذها كلها ضمن طلب المستخدم.
- توجد اختبارات للمسارات العامة، metadata المكررة، sitemap، cache headers، وصلاحيات/تنظيف المدخلات.
- يستخدم `vite.config.js` تقسيمًا لحزم الإدارة، ولا تظهر حزم Tiptap/Charts في قائمة imports الأساسية لمدخل React الرئيسي في manifest الحالي.

## بوابة القبول قبل الدمج

لا تُدمج تغييرات الموقع حتى تمر الاختبارات على هذا الفرع نفسه:

1. `npm run lint`
2. `php artisan test`
3. `npm run build` — إلزامي، ويتضمن بناء العميل وSSR وprerender.
4. `npx playwright test` على التطبيق المحلي الذي شُغّل من نفس checkout، وليس على الإنتاج.
5. مراجعة جميع تغييرات الفرع ونتيجة GitHub Actions، وفحص صفحات الجوال وRTL/LTR والصور والـ SEO. فشل أو تعذر أي بوابة يجب أن يبقى موضحًا ولا يُعامل على أنه نجاح.

**الحالة وقت كتابة هذا التقرير:** التغييرات أُنشئت على فرع منفصل، ولم تُدمج في `main`. حالة البناء والاختبارات الفعلية ستُحدّث بعد ظهور نتائج GitHub Actions؛ هذا التقرير لا يدّعي نجاح اختبارات لم تُنفذ.
